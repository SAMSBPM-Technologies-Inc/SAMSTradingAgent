## 2. Local Development Setup

### Prerequisites

- Python 3.11+
- Node.js 20+
- MongoDB 7 (local instance or Docker)

### Quick Start

```bash
# Clone the repository
git clone <repo-url>
cd SAMSTradingAgent

# ── Backend ──────────────────────────────────────────────
cd backend
python -m venv .venv && source .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env   # then edit .env with your keys

# Start the API server
uvicorn app.main:app --reload
# API is now running at http://localhost:8000
# Swagger UI:  http://localhost:8000/docs
# ReDoc:       http://localhost:8000/redoc

# ── Frontend (separate terminal) ─────────────────────────
cd frontend
npm install
cp .env.example .env   # set VITE_API_BASE_URL=http://localhost:8000
npm run dev
# Frontend is now running at http://localhost:5173
```

### Docker (Backend + MongoDB together)

```bash
cd backend
docker compose up --build
```

This starts `trading_agent_api` on port 8000 and `trading_mongo` on port 27017 with a persistent `mongo_data` volume.

### Minimum .env for local development

```dotenv
MONGODB_URL=mongodb://localhost:27017
MONGODB_DB_NAME=trading_agent
APP_ENV=development
JWT_SECRET_KEY=dev-secret-change-in-prod
ENABLE_AI_ANALYST=false
ENABLE_ML_MODEL=false

# Optional — services degrade gracefully without these
FINNHUB_API_KEY=
FRED_API_KEY=
ANTHROPIC_API_KEY=
```

Without `FINNHUB_API_KEY`, ticker search and real news sentiment are unavailable; VADER sentiment runs on any headlines fetched. Without `FRED_API_KEY`, macro scores default to 0.5 (neutral). Without `ANTHROPIC_API_KEY`, the system falls back to the rule-based signal generator.

## 3. Adding a New Data Source

The canonical example is `macro.py` (FRED API). Use this pattern for any new external data source.

### Step 1 — Create the service module

Create `backend/app/services/my_source.py` with an async fetch function:

```python
async def fetch_my_data(ticker: str) -> dict:
    """
    Fetch data from MySource API.
    Returns a dict that always includes a 'source' key for provenance tracking.
    On failure, log a warning and return a safe default — never raise.
    """
    try:
        # ... your async fetch logic here ...
        return {
            "source": "mysource",
            "some_value": 42.0,
        }
    except Exception as exc:
        logger.warning("my_source_failed", ticker=ticker, error=str(exc))
        return {"source": "error", "some_value": None}
```

Key conventions:
- Always run blocking I/O (e.g., `yfinance`) via `asyncio.to_thread()` — never call sync libraries directly in an `async def`
- Always include a `"source"` key in the returned dict — this is used by `pipeline.py` for provenance tracking in `_build_data_sources()`
- Return a safe default dict on failure rather than raising

### Step 2 — Add to ingestion.py

Import your function and add it to the `asyncio.gather()` call in `_fetch_enrichment`:

```python
from app.services.my_source import fetch_my_data

async def _fetch_enrichment(ticker: str) -> tuple[...]:
    my_task = fetch_my_data(ticker)

    sentiment, headlines, fundamentals, macro, alternative, my_data = await asyncio.gather(
        sentiment_task,
        headlines_task,
        fundamentals_task,
        macro_task,
        alt_task,
        my_task,
        return_exceptions=True,
    )

    if isinstance(my_data, Exception):
        logger.warning("my_source_exception", ticker=ticker, error=str(my_data))
        my_data = {"source": "exception", "some_value": None}

    return sentiment, headlines, fundamentals, macro, alternative, my_data
```

### Step 3 — Store in the raw doc

Add your data to the `doc` dict in `ingest_ticker()`:

```python
doc = {
    "ticker": ticker,
    # ... existing fields ...
    "my_data": my_data,
}
```

### Step 4 — Use in feature engineering

In `feature_engineering.py`, read the stored value from `raw_doc` and compute a sub-score:

```python
my_data = raw_doc.get("my_data", {})
my_score = _compute_my_score(my_data)  # returns 0.0–1.0

feature_doc = {
    # ... existing fields ...
    "my_score": round(my_score, 4),
}
```

### Step 5 — Include in scoring (optional)

If you want the new source to affect the composite score, add it to `scoring.py` `_weighted_score()`. Remember: the six base weights (`weight_technical`, `weight_fundamental`, `weight_sentiment`, `weight_macro`, `weight_volatility`, `weight_catalyst`) must sum to exactly 1.0. If you add a seventh to the base sum, update the `validate_weights_sum` validator in `config.py` accordingly.

### Step 6 — Expose to the AI analyst (optional)

If the data is useful context for the AI narrative, add it to the prompt context in `analyst.py` `_build_context()`.

## 4. Adding a New API Endpoint

### Step 1 — Choose or create a router file

For a feature that fits an existing domain, add the route to the appropriate file in `backend/app/routes/`. For a genuinely new domain, create `backend/app/routes/my_feature.py`:

```python
from fastapi import APIRouter, Depends
from app.dependencies import get_current_user

router = APIRouter(prefix="/my-feature", tags=["my-feature"])
```

### Step 2 — Define Pydantic models

Add request and response models to `backend/app/models/stock.py`:

```python
class MyRequest(BaseModel):
    ticker: str
    some_param: Optional[str] = None

class MyResponse(BaseModel):
    ticker: str
    result: float
    generated_at: datetime
```

### Step 3 — Implement the route

```python
@router.get("/{ticker}", response_model=MyResponse)
async def get_my_feature(
    ticker: str,
    current_user: dict = Depends(get_current_user),  # required for auth
) -> MyResponse:
    # ... implementation ...
    return MyResponse(ticker=ticker, result=0.5, generated_at=utcnow())
```

All routes that should require authentication must include `current_user: dict = Depends(get_current_user)` in the signature. Routes without this dependency are public.

### Step 4 — Register the router in main.py

```python
from app.routes import my_feature

# In create_app():
app.include_router(my_feature.router)
```

### Step 5 — Add the API call to the frontend

In `frontend/src/lib/api.ts`, add a typed helper:

```typescript
export const myFeatureApi = {
  get: (ticker: string) =>
    api.get<MyResponse>(`/my-feature/${ticker}`),
}
```

The `api` Axios instance already handles Bearer token injection via its request interceptor, so you do not need to add auth headers manually.

## 6. MongoDB Operations

All collection names are defined as constants in `backend/app/db.py`. Always import and use these constants rather than hardcoding string names.

```python
from app.db import (
    COLL_RAW,            # "stocks_raw"
    COLL_FEATURES,       # "stocks_features"
    COLL_SIGNALS,        # "stocks_signals"
    COLL_SIGNAL_HISTORY, # "stocks_signal_history"
    COLL_WATCHED,        # "watched_tickers"
    COLL_USERS,          # "users"
    get_db,
)
```

### Common patterns

```python
from app.db import get_db, COLL_SIGNALS

db = await get_db()

# Find one document
doc = await db[COLL_SIGNALS].find_one({"ticker": "PLTR"})

# Find multiple documents
docs = await db[COLL_SIGNALS].find({"signal": "BUY"}).to_list(length=100)

# Upsert (replace entire document, create if not exists)
await db[COLL_SIGNALS].replace_one({"ticker": ticker}, doc, upsert=True)

# Update specific fields only
await db[COLL_SIGNALS].update_one(
    {"ticker": ticker},
    {"$set": {"score": 0.8, "signal": "BUY"}},
)

# Conditional upsert (only set fields on insert, not on update)
await db[COLL_SIGNAL_HISTORY].update_one(
    {"ticker": ticker, "hour_bucket": hour_bucket},
    {"$setOnInsert": record, "$set": {"hour_bucket": hour_bucket}},
    upsert=True,
)
```

### Indexes

Indexes are created idempotently on every app startup in `db._ensure_indexes()`. If you add a new collection or query pattern that needs an index, add it there. The function is safe to call repeatedly — MongoDB silently skips index creation if the index already exists.

### User IDs and ObjectId

There is a type mismatch between how MongoDB stores user IDs and how they are referenced in other collections:

- In the `users` collection: `_id` is a MongoDB `ObjectId`
- In `watched_tickers`: `user_id` is stored as a **string** (via `str(user["_id"])`)

When querying by user ID across collections:

```python
from bson import ObjectId

# Store user_id as string:
user_id_str = str(user["_id"])

# Query users by string user_id from another collection:
user = await db[COLL_USERS].find_one({"_id": ObjectId(user_id_str)})
```

Never store `ObjectId` directly in `watched_tickers.user_id` — it is always a string there. When loading users from a list of string IDs:

```python
user_ids = [ObjectId(uid) for uid in user_id_strings if uid]
users = await db[COLL_USERS].find({"_id": {"$in": user_ids}}).to_list(length=500)
```

## 7. Modifying the Scoring Formula

The scoring system has two modes, controlled by `ENABLE_ML_MODEL` in `.env`.

### Weighted Linear Scoring (default)

The primary scoring formula lives in `backend/app/services/scoring.py` in `_weighted_score()`:

```python
def _weighted_score(feat: dict, settings) -> float:
    base = (
        settings.weight_technical   * feat.get("technical_score",   0.5)
        + settings.weight_fundamental * feat.get("fundamental_score", 0.5)
        + settings.weight_sentiment   * feat.get("sentiment_score",   0.5)
        + settings.weight_macro       * feat.get("macro_score",       0.5)
        + settings.weight_volatility  * feat.get("volatility_score",  0.5)
        + settings.weight_catalyst    * feat.get("catalyst_score",    0.5)
    )
    alt_modifier = settings.weight_alternative_data * (
        feat.get("alternative_data_score", 0.5) - 0.5
    )
    return base + alt_modifier
```

The **six base weights** are configured in `backend/app/config.py` and their default values are:

| Weight | Default | Description |
|--------|---------|-------------|
| `weight_technical` | 0.25 | RSI, MACD, Bollinger, Stoch RSI, MA cross |
| `weight_sentiment` | 0.20 | News sentiment score |
| `weight_fundamental` | 0.15 | PE, revenue growth, FCF, D/E |
| `weight_macro` | 0.15 | VIX, yield curve, CPI |
| `weight_catalyst` | 0.15 | Volume anomaly + recent headlines |
| `weight_volatility` | 0.10 | Inverse of 20-day annualized volatility |

**These six weights must sum to exactly 1.0.** A `model_validator` in `config.py` enforces this at startup — a mismatch crashes the app with a descriptive error. To override weights, set them in `.env`:

```dotenv
WEIGHT_TECHNICAL=0.30
WEIGHT_SENTIMENT=0.15
WEIGHT_FUNDAMENTAL=0.15
WEIGHT_MACRO=0.15
WEIGHT_CATALYST=0.15
WEIGHT_VOLATILITY=0.10
```

`weight_alternative_data` (default 0.10) is a separate **additive modifier** and does not participate in the sum. It shifts the composite score by `±0.05` at maximum. This allows alternative data to influence the score without requiring the sum-to-1.0 base weights to change.

### Sub-scores

Each sub-score (0.0–1.0) is computed in `backend/app/services/feature_engineering.py`:

- `_technical_score()`: weighted combination of RSI, MACD, Bollinger %B, Stoch RSI, MA cross (weights 25/25/20/15/15)
- `_fundamental_score()`: analyst recommendation, revenue growth, PE ratio, FCF sign, D/E ratio
- `_macro_score()`: VIX (35%), yield curve spread (35%), CPI YoY (30%)
- `_volatility_score()`: inverse of annualized 20-day volatility (lower vol = higher score)
- `_catalyst_score()`: in `catalyst.py`, based on volume anomaly and headline recency
- `_alternative_data_score()`: in `alternative_data.py`, options P/C ratio (50%) + insider buy ratio (50%)

All sub-scores default to 0.5 (neutral) when data is unavailable.

## 8. Retraining the XGBoost Model

The XGBoost model is an optional enhancement (requires `ENABLE_ML_MODEL=true`). The trained model file is `backend/model/xgb_scorer.json`.

### Training

```bash
cd backend
export FRED_API_KEY=your-fred-key   # required for macro features
python scripts/train_xgb.py
# Output: backend/model/xgb_scorer.json
```

Training details:
- **Universe**: 30 large-cap US equities across sectors
- **History**: 3 years of daily OHLCV data
- **Label**: 20-day forward return (regression target, clipped to [-0.5, 0.5])
- **Features**: 14 (see below)
- **Inference normalization**: raw XGBoost output is passed through `clamp()` to [0, 1]

### The 14-Feature Vector

The feature vector order must be **identical** between `train_xgb.py` and `scoring.py _ml_score()`. Any mismatch produces silently wrong predictions (the model loads successfully but uses the wrong features).

```
Index  Feature            Source
0      rsi_14             feature_engineering.py
1      macd_bullish       feature_engineering.py (1.0 or 0.0)
2      bb_pct             feature_engineering.py
3      stoch_rsi          feature_engineering.py
4      ma_cross_bullish   feature_engineering.py (1.0 or 0.0)
5      volume_anomaly     feature_engineering.py (ratio vs 20-day avg)
6      volatility_20d     feature_engineering.py (annualized)
7      technical_score    feature_engineering.py
8      fundamental_score  FROZEN at 0.5 (training data had no real values)
9      sentiment_score    FROZEN at 0.5 (training data had no real values)
10     macro_score        feature_engineering.py
11     volatility_score   feature_engineering.py
12     catalyst_score     feature_engineering.py
13     vix                stored in feature doc from macro.py
```

**Important caveats:**

- `fundamental_score` (index 8) and `sentiment_score` (index 9) are frozen at 0.5 in both training and inference because historical values for these features were unavailable when the model was trained. Until the model is retrained with real historical fundamental and sentiment data, these features must remain frozen at 0.5 in `_ml_score()`.
- If you add a new feature to the inference vector, you **must** retrain the model and update `train_xgb.py` to match. The feature count (14) is baked into the saved model.

### Enabling the Model

```dotenv
ENABLE_ML_MODEL=true
```

If `xgb_scorer.json` is missing, `scoring.py` logs a warning and falls back to the weighted formula transparently.

## 9. Signal History and Performance Tracking

### Appending History

Every successful pipeline run calls `_append_history()` in `pipeline.py`. This function upserts a record to `stocks_signal_history` keyed on `(ticker, hour_bucket)`:

```python
hour_bucket = now.replace(minute=0, second=0, microsecond=0)

await db[COLL_SIGNAL_HISTORY].update_one(
    {"ticker": signal["ticker"], "hour_bucket": hour_bucket},
    {"$setOnInsert": record, "$set": {"hour_bucket": hour_bucket}},
    upsert=True,
)
```

The `(ticker, hour_bucket)` composite unique index means multiple pipeline runs within the same clock hour produce only one history record. Do not replace this with `insert_one` — it will create duplicates.

Each history record includes `price_at_signal` (set from `raw_doc["current_price"]` during ingestion). Records where `price_at_signal` is None cannot be settled and are excluded from performance calculations.

### Settling History (Performance Tracker)

Settlement runs in `_performance_tracker_job()` in `scheduler.py`, triggered daily at 06:00 UTC. It finds records that are at least 28 calendar days old (covering approximately 20 trading days) and have `return_20d = None`.

For each unsettled record, it fetches the current price from Yahoo Finance and computes:

```python
ret = (current_price - price_at_signal) / price_at_signal
was_correct = (ret > 0) if signal == "BUY" else (ret < 0) if signal == "SELL" else None
```

HOLD signals are not directional and `was_correct` remains `None` for them.

The Performance API endpoint aggregates these settled records to compute win rates and average returns by signal type and ticker.

## 11. Logging

The app uses `structlog` with structured key=value output.

### Usage

```python
from app.utils.logger import get_logger
logger = get_logger(__name__)

# Key=value structured logging — always use keyword arguments
logger.info("pipeline_start", ticker="PLTR")
logger.info("scored", ticker="PLTR", composite=0.74, method="weighted")
logger.warning("source_failed", ticker="PLTR", source="finnhub", error=str(exc))
logger.error("unhandled_exception", path="/analyze", error=str(exc))
```

### Output format

- **Development** (`APP_ENV=development`): human-readable colored console output via `structlog.dev.ConsoleRenderer()`
- **Production**: JSON to stdout, one JSON object per log line, captured by Docker/your log aggregator

The log level is controlled by `LOG_LEVEL` in `.env` (default: `INFO`). Set to `DEBUG` during local development to see cache hits, scheduler skips, and other verbose events.

### Structured fields to include

Follow the convention used throughout the codebase:

- Always include `ticker=ticker` for any ticker-scoped event
- Use snake_case for event names: `"pipeline_start"`, `"cache_hit"`, `"alert_settings_updated"`
- Include `error=str(exc)` in warning/error events, not the exception object itself (structlog handles formatting)

## 12. Common Pitfalls

### Blocking the event loop

Never call synchronous, blocking code directly inside an `async def` function. This freezes the entire server while the call runs.

```python
# WRONG — blocks the event loop
async def bad_example(ticker: str) -> dict:
    import yfinance as yf
    info = yf.Ticker(ticker).info   # sync call, blocks everything
    return info

# CORRECT — runs sync code in a thread pool
async def good_example(ticker: str) -> dict:
    import asyncio
    import yfinance as yf
    info = await asyncio.to_thread(lambda: yf.Ticker(ticker).info)
    return info
```

The same applies to `requests`, `time.sleep()`, `fredapi`, and any other synchronous library. All such calls in the codebase go through `asyncio.to_thread()`.

### Score weight validation

The six base scoring weights in `config.py` must sum to exactly 1.0. The `validate_weights_sum` validator runs at startup and raises a `ValueError` if the sum deviates by more than 1e-6. If you add a new weight to the six-weight sum (e.g., because you are adding a new sub-score to the base), update both the default value and the validator to include your new weight in the sum.

Note: `weight_alternative_data` is intentionally excluded from the sum — it is a modifier coefficient, not a base weight.

### XGBoost feature order

The 14-feature vector in `scoring.py _ml_score()` must exactly match the feature order in `train_xgb.py`. XGBoost does not validate feature names at inference — it uses positional indexing. A mislabeled feature produces wrong predictions silently. Any change to the feature vector (adding, removing, or reordering) requires retraining the model.

### MongoDB ObjectId

User IDs have a type asymmetry between collections:

- `users._id` is a MongoDB `ObjectId`
- `watched_tickers.user_id` is a **string** (stored with `str(user["_id"])`)

Always convert with `str(user["_id"])` when writing to `watched_tickers`, and convert back with `ObjectId(uid)` when querying `users`.

### Idempotent history records

The `_append_history()` function in `pipeline.py` uses an upsert keyed on `(ticker, hour_bucket)` with `$setOnInsert`. This is intentional — it makes the operation idempotent so multiple pipeline runs within the same hour produce exactly one record. Do not replace this with `insert_one`.

### Cache TTL and force refresh

The `/analyze` endpoint caches results for 30 minutes (`_CACHE_TTL_MINUTES = 30` in `analysis.py`). Cached results skip the pipeline entirely and return the stored signal. To bypass the cache during development or testing, append `?force_refresh=true` to the request:

```
GET /analyze?ticker=PLTR&force_refresh=true
```

The frontend refresh button sends this parameter automatically.

### Scheduler runs only during market hours

`_market_pipeline_job()` checks `_is_market_hours()` before running. During local development outside 9:30–16:00 ET on weekdays, the pipeline will not run on the interval trigger. To test the pipeline directly, call `POST /analyze?ticker=AAPL&force_refresh=true` or invoke `run_pipeline("AAPL")` in a Python shell. The premarket sweep (08:00 ET) and performance tracker (06:00 UTC) run regardless of market hours.

### Finnhub ticker search dependency

The `/ticker/search` endpoint requires `FINNHUB_API_KEY`. Without it, the endpoint returns HTTP 503. In local development, either set a Finnhub key (free tier is sufficient) or add tickers manually via the `/ticker` POST endpoint using curl or the Swagger UI.
