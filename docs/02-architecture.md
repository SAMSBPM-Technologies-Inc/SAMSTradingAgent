## 1. System Overview

SAMSTradingAgent is built on a classic three-tier architecture:

```
React Frontend  →  FastAPI Backend  →  MongoDB + External APIs
```

**Tier 1 — Presentation (React + Vite + TypeScript)**
A single-page application (SPA) served from Cloudflare Pages. The frontend communicates exclusively with the FastAPI backend via authenticated REST API calls. It is stateless and holds no business logic beyond UI rendering and local preference persistence (theme, JWT token).

**Tier 2 — Application (FastAPI, Python 3.11)**
The backend exposes a REST API structured around 8 route modules. A service layer of 15 services handles all domain logic: data ingestion, feature engineering, scoring, signal generation, AI analyst report generation, notifications, and performance settlement. A job layer (APScheduler) drives the background pipeline and scheduled tasks.

**Tier 3 — Data (MongoDB, Docker)**
MongoDB stores all persistent state: raw ingested data, computed features, signals, signal history for settlement, user accounts, and watchlists. Collections are indexed for fast lookup by ticker (unique) and by user/ticker compound key.

**Cross-Cutting Concerns**
- All external traffic enters via a Cloudflare Tunnel — the backend port is never publicly exposed.
- Structured JSON logging via `structlog` provides observability.
- Docker Compose with restart policies provides process-level fault tolerance on a Hetzner VPS.

## 3. Backend Architecture

### 3.1 Application Layer (FastAPI)

**Entry point:** `backend/app/main.py`

The application bootstraps via FastAPI's `lifespan` context manager, which:
1. Opens the MongoDB connection (Motor async client) and pings the server.
2. Starts the APScheduler `BackgroundScheduler` with all four registered jobs.
3. On shutdown, shuts down the scheduler and closes the MongoDB connection.

**Middleware and cross-cutting configuration:**
- `CORSMiddleware`: configured with an explicit `allow_origins` list read from the `ALLOWED_ORIGINS` environment variable. Wildcard origins are not permitted in production.
- Global exception handler: catches all unhandled `Exception` instances, logs them with `structlog` at ERROR level (including traceback), and returns a standardized JSON `{"detail": "Internal server error"}` with HTTP 500.

**Route modules (8 routers):**

| Router Module | Prefix | Key Endpoints |
|---|---|---|
| `routes/health.py` | `/health` | `GET /health` — liveness check |
| `routes/auth.py` | `/auth` | `POST /auth/login`, `GET /auth/me`, `PUT /auth/me`. There is no register endpoint — accounts are provisioned |
| `routes/admin.py` | `/admin` | `GET/POST /admin/users`, `PATCH /admin/users/{id}`, `GET /admin/access-requests`. Gated on `ADMIN_EMAIL` |
| `routes/analysis.py` | — | `GET /analyze` — trigger/return signal for a single ticker |
| `routes/signals.py` | `/signals` | `GET /signals` — fetch current signal documents |
| `routes/watchlist.py` | `/watchlist` | `GET`, `POST /watchlist/add`, `DELETE /watchlist/remove` |
| `routes/report.py` | `/report` | `GET /report/{ticker}` — fetch AI analyst report |
| `routes/performance.py` | `/performance` | `GET /performance` — settled signal statistics |
| `routes/alerts.py` | `/alerts` | `PUT /alerts/settings`, `POST /alerts/test` |

**Authentication dependency:**
All protected endpoints use `Depends(get_current_user)` from `app/dependencies.py`. This dependency extracts the JWT from the `Authorization: Bearer <token>` header, verifies the signature and expiry, looks up the user in MongoDB, and returns the user document. A missing, malformed, or expired token raises HTTP 401.

### 3.2 Service Layer

The service layer (`backend/app/services/`) contains 15 modules. Each service is responsible for a single domain concern.

---

#### `ingestion.py`
**Purpose:** Fetch all raw data needed for a single ticker from external APIs, and persist it to `stocks_raw`.

Key design decisions:
- Runs external API calls concurrently using `asyncio.gather` where the APIs are independent (e.g., FRED macro data can be fetched in parallel with Finnhub news).
- Yahoo Finance OHLCV and fundamentals use `yfinance.Ticker` (synchronous), called via `asyncio.run_in_executor` to avoid blocking the event loop.
- Alternative data (options chain, insider transactions) is fetched via the same `yfinance.Ticker` object and stored in the raw document under `alternative_data`.
- On any individual API failure, that sub-field is set to a safe default and a warning is logged. The overall ingestion call does not raise an exception unless price data (OHLCV) is unavailable.

**Output:** Upserts one document into `stocks_raw` with fields:
`ticker`, `bars` (list of OHLCV dicts), `current_price`, `sentiment_raw`, `fundamentals`, `macro`, `alternative_data`, `ingested_at`.

---

#### `feature_engineering.py`
**Purpose:** Compute all 14 technical indicators and 7 sub-scores from the raw data stored in `stocks_raw`.

**Technical indicators computed:**

| Indicator | Computation |
|---|---|
| RSI-14 | 14-period Wilder RSI using closing prices |
| MACD | 12/26 EMA difference; 9-period signal line; histogram |
| Bollinger Bands | 20-period SMA ± 2 standard deviations; band width |
| MA-20 | 20-period simple moving average of close |
| MA-50 | 50-period simple moving average of close |
| ATR | 14-period Average True Range |
| Volume Ratio | Current volume / 20-period average volume |
| Price vs MA20 | (price − MA20) / MA20 × 100 |
| Price vs MA50 | (price − MA50) / MA50 × 100 |
| MA Cross | MA20 / MA50 ratio (>1 = bullish alignment) |
| MACD Histogram | MACD line − signal line |
| RSI Momentum | RSI vs 50 midpoint |
| BB Position | (price − lower band) / (upper band − lower band) |
| Volume Trend | Current volume vs previous period volume |

**Sub-scores computed (each 0–100):**

| Sub-Score | Primary Inputs |
|---|---|
| `trend_score` | MA-20 vs MA-50 alignment, price vs MAs |
| `momentum_score` | RSI-14, MACD histogram direction |
| `volatility_score` | Bollinger Band width, ATR relative to price |
| `volume_score` | Volume ratio vs average |
| `fundamental_score` | P/E, revenue growth, FCF margin, debt/equity |
| `sentiment_score` | Finnhub news VADER compound score |
| `macro_score` | FRED: Fed Funds Rate, CPI, VIX, yield curve slope |

**Output:** Upserts one document into `stocks_features` containing all indicators, all sub-scores, and a preliminary `composite_score` (pre-alternative-data).

---

#### `scoring.py`
**Purpose:** Compute the final composite score (0–100) from the 7 sub-scores and apply an alternative data modifier.

Two scoring modes are supported, selected at startup:

**Mode A — Linear weighted sum (default):**
```
composite = (
    trend_score     × 0.25 +
    momentum_score  × 0.20 +
    fundamental_score × 0.20 +
    sentiment_score × 0.15 +
    macro_score     × 0.10 +
    volatility_score × 0.05 +
    volume_score    × 0.05
)
```

**Mode B — XGBoost model (optional, `ENABLE_XGBOOST=true`):**
When enabled, the 7 sub-scores are fed into a trained XGBoost regressor loaded from `backend/model/`. The model outputs a predicted score in the 0–100 range. If the model file is absent or fails to load, scoring falls back to Mode A automatically.

**Alternative data modifier:**
After the base composite score is computed, an additive modifier is applied based on:
- Options put/call ratio (bullish < 0.7: +modifier, bearish > 1.2: −modifier)
- Short interest % (high short interest > 15%: small negative modifier)
- Insider net buying (net buys > 0: small positive modifier)

The modifier is bounded to ±10 points to prevent alternative data from dominating the signal.

**Output:** Returns the final composite score. The score is written to `stocks_features` and subsequently to `stocks_signals`.

---

#### `risk_engine.py`
**Purpose:** Compute a risk score (0–10, where 10 = highest risk) for context alongside the signal.

Inputs:
- RSI-14 (overbought/oversold territory)
- ATR as a percentage of price (historical volatility proxy)
- VIX level from FRED macro data (market-wide fear gauge)

The risk score is included in the signal output and is used by `signal_generator.py` to narrow confidence bands when risk is elevated.

---

#### `signal_generator.py`
**Purpose:** Convert the composite score into a BUY/SELL/HOLD signal with entry price, price target, stop loss, time horizon, and confidence percentage.

Signal thresholds (configurable via environment variables):
```
composite_score >= BUY_THRESHOLD  (default: 62)  → BUY
composite_score <= SELL_THRESHOLD (default: 38)   → SELL
otherwise                                          → HOLD
```

Confidence is computed as the normalized distance of the composite score from the nearest threshold boundary, bounded 0–100%.

Price target and stop loss are computed using ATR-based multiples:
- BUY: target = price + 2.5 × ATR; stop = price − 1.5 × ATR
- SELL: target = price − 2.5 × ATR; stop = price + 1.5 × ATR
- HOLD: target and stop are symmetric around current price

Time horizon is **judged by the analyst, not computed** — there has never been a
rule mapping ATR to a horizon, and this line previously described one. It is
constrained to four buckets by the response schema (`analyst._TIME_HORIZONS`),
and the system prompt directs the model to derive it from the earnings and
catalyst dates in its context and from how far the price target sits from spot
in ATR. Until 1.29.0 it was an unconstrained, unmentioned string, and every
ticker came back "3-6 months".

---

#### `pipeline.py`
**Purpose:** Orchestrator that runs the full analysis sequence for a single ticker end-to-end. This is the central service called by both the API (`/analyze` endpoint) and the background scheduler.

Execution sequence for a single ticker:
```
1. ingestion.run(ticker)           → stocks_raw
2. feature_engineering.run(ticker) → stocks_features
3. scoring.run(ticker)             → composite_score
4. risk_engine.run(ticker)         → risk_score
5. signal_generator.run(ticker)    → signal, confidence, targets
6. analyst.run(ticker)             → analyst_output  (async, Claude API)
7. alternative_data.get(ticker)    → options, short interest, insider
8. Upsert stocks_signals document
9. Change detection: compare to previous signal
10. If changed: fire notifier.send_alert() and upsert stocks_signal_history
```

The pipeline is the single source of truth for the `stocks_signals` collection. All reads of signal data query `stocks_signals`; all writes go through `pipeline.run()`.

---

#### `analyst.py`
**Purpose:** Generate an AI analyst report for a ticker by calling the Anthropic Claude API.

Context construction:
- Pulls computed sub-scores, technical indicators, fundamentals, macro conditions, and the signal from the current pipeline run.
- Constructs a structured prompt that instructs Claude to respond in a specific JSON schema containing: `thesis`, `bull_case` (list), `bear_case` (list), `catalysts` (list), `analyst_note`, and `sentiment` (string).

API call:
- Uses `anthropic.AsyncAnthropic` client for non-blocking I/O.
- Model: `claude-3-5-sonnet` (configurable via `ANTHROPIC_MODEL` env var).
- Max tokens: 1,024 (sufficient for the structured JSON response).

Response parsing:
- Parses the JSON response from Claude's message content.
- If parsing fails (malformed JSON, unexpected schema), falls back to the rule-based report generator.
- Logs parse errors at WARNING level.

Fallback (rule-based):
- Constructs a template-based report from the sub-score values and indicator readings.
- Marks the report with `source: "rule_based"` so the UI can display a badge.

---

#### `alternative_data.py`
**Purpose:** Retrieve options flow, short interest, and insider transaction data from Yahoo Finance via `yfinance`.

Data retrieved per ticker:
- **Options:** Nearest expiry call and put option chains → aggregate open interest → put/call ratio
- **Short interest:** `info["shortPercentOfFloat"]` (percentage of float sold short)
- **Insider transactions:** `insider_transactions` DataFrame → count of buy vs. sell transactions over trailing 90 days

All three data points are stored in `stocks_raw.alternative_data` and carried forward into `stocks_signals`.

---

#### `catalyst.py`
**Purpose:** Compute a volume-anomaly catalyst score that identifies unusual trading activity as a potential near-term catalyst.

The catalyst score compares the most recent day's volume against the 20-day average volume. A ratio significantly above 1.0 (e.g., > 2.0) indicates unusual institutional or retail interest and boosts the catalyst sub-score. The catalyst score is included in the signal output for user context.

---

#### `fundamentals.py`
**Purpose:** Extract fundamental financial ratios from yfinance and compute the `fundamental_score` sub-score.

Metrics extracted:
| Metric | yfinance field | Scoring direction |
|---|---|---|
| P/E Ratio | `trailingPE` | Lower is better (bounded) |
| Revenue Growth | `revenueGrowth` | Higher is better |
| Free Cash Flow Margin | `freeCashflow` / `totalRevenue` | Higher is better |
| Debt-to-Equity | `debtToEquity` | Lower is better |

Missing data fields are substituted with neutral values to prevent NaN propagation into the composite score.

---

#### `macro.py`
**Purpose:** Fetch macroeconomic indicators from the FRED API and compute the `macro_score` sub-score.

FRED series fetched:
| FRED Series | Indicator | Signal interpretation |
|---|---|---|
| `FEDFUNDS` | Federal Funds Rate | High rates → bearish for equities |
| `CPIAUCSL` | CPI (YoY change) | High inflation → negative modifier |
| `VIXCLS` | CBOE VIX | High VIX → high risk environment |
| `T10Y2Y` | 10Y−2Y yield spread | Inverted curve → negative macro |

FRED data changes infrequently (daily or monthly). The macro service caches its results in `stocks_raw.macro` and only re-fetches from FRED when the cached data is more than 24 hours old.

---

#### `news.py`
**Purpose:** Fetch recent news headlines from Finnhub and compute a VADER sentiment score.

Process:
1. Call Finnhub `/company-news` endpoint for the ticker, filtered to the last 7 days.
2. Run each headline through `vaderSentiment.SentimentIntensityAnalyzer`.
3. Average the compound scores across all headlines (range: −1.0 to +1.0).
4. Normalize to a 0–100 sub-score for use in feature engineering.

If Finnhub returns no headlines or an error, the sentiment sub-score defaults to 50 (neutral).

---

#### `notifier.py`
**Purpose:** Send alert notifications to Slack and/or WhatsApp.

**Slack:** Uses incoming webhook URLs. Formats a Block Kit message payload with the ticker, signal, score, confidence, and price. Sends via `httpx.AsyncClient.post`.

**WhatsApp (CallMeBot):** Encodes the message as a URL-encoded string and calls the CallMeBot API endpoint with the user's phone number and API key. CallMeBot delivers the message to the user's WhatsApp.

The notifier respects per-user alert settings: if a user has disabled Slack or WhatsApp alerts, the corresponding channel is skipped. If delivery fails, the error is logged at WARNING level and the calling pipeline is not interrupted.

---

#### `backtesting.py`
**Purpose:** Stub service for future backtesting capability. Currently a no-op.

Controlled by the `ENABLE_BACKTESTING=true` environment variable. When disabled (default), the backtesting endpoints return `{"status": "disabled"}`. The service exists as a scaffold and is not integrated into the main pipeline. It is excluded from all production SLA guarantees.

---

#### `auth.py`
**Purpose:** Authentication helper functions used by the `routes/auth.py` router.

Functions:
- `hash_password(plain: str) → str` — bcrypt hash with configurable rounds (default: 12)
- `verify_password(plain: str, hashed: str) → bool` — bcrypt comparison
- `create_access_token(data: dict) → str` — signs a JWT with HS256, adds `exp` claim
- `decode_access_token(token: str) → dict` — verifies signature and expiry, returns claims

### 3.3 Job Layer (APScheduler)

**File:** `backend/app/jobs/scheduler.py`

The application uses APScheduler's `BackgroundScheduler` (thread-based). All jobs are registered during the lifespan startup and run in background threads. Jobs that interact with MongoDB use Motor's synchronous-compatible patterns or create their own event loops as needed.

| Job Name | Trigger Type | Schedule | Purpose |
|---|---|---|---|
| `market_pipeline` | Interval | Every N minutes (configurable, default 30 min) | Run `pipeline.run()` for all watched tickers. Skips execution if current time is outside market hours (9:30–16:00 ET, Mon–Fri) or if the day is a US market holiday. |
| `premarket_sweep` | Cron | `hour=8, minute=0` ET, Mon–Fri | Full refresh of all watched tickers before market open. Ensures signals are populated at the 9:30 ET open. |
| `perf_tracker` | Cron | `hour=6, minute=0` UTC daily | Signal settlement job. Finds all `stocks_signal_history` records that are 20+ days old and unsettled, fetches current prices, computes returns, writes `was_correct` and `return_20d`. |
| `daily_digest` | Cron | `hour=9, minute=0` ET, Mon–Fri | Queries all users with alert settings enabled, summarizes their watchlist signals, and sends a digest via Slack or WhatsApp. |

Market hours guard (for `market_pipeline`):
```python
now_et = datetime.now(pytz.timezone("America/New_York"))
if now_et.weekday() >= 5:  # Saturday or Sunday
    return
if not (time(9, 30) <= now_et.time() <= time(16, 0)):
    return
```

## 4. Data Flow

### 4.A User-Triggered Analysis: `GET /analyze?ticker=PLTR`

```
1. HTTP GET /analyze?ticker=PLTR
   Authorization: Bearer <jwt>
   │
   ▼
2. FastAPI router: routes/analysis.py
   → Depends(get_current_user)
     → decode JWT → lookup user in MongoDB
     → If invalid: return HTTP 401

3. Check stocks_signals collection for existing document:
   db.stocks_signals.find_one({"ticker": "PLTR"})
   │
   ├── Document exists AND (updated_at > now − 30 min) AND force_refresh=false
   │     → Return cached document as JSON response  ─────────────────────────► HTTP 200
   │
   └── No document OR cache expired OR force_refresh=true
         │
         ▼
4. pipeline.run("PLTR")
   │
   ├── 4a. ingestion.run("PLTR")
   │     ├── yfinance.download("PLTR", period="90d") → OHLCV bars
   │     ├── yfinance.Ticker("PLTR").info → fundamentals
   │     ├── yfinance.Ticker("PLTR").option_chain() → options data
   │     ├── yfinance.Ticker("PLTR").insider_transactions → insider data
   │     ├── finnhub.client.company_news("PLTR") → news headlines
   │     ├── fred.get_series(["FEDFUNDS","CPIAUCSL","VIXCLS","T10Y2Y"]) → macro
   │     └── Upsert → stocks_raw["PLTR"]
   │
   ├── 4b. feature_engineering.run("PLTR")
   │     ├── Compute 14 technical indicators from bars
   │     ├── Compute 7 sub-scores (trend, momentum, volatility,
   │     │   volume, fundamental, sentiment, macro)
   │     └── Upsert → stocks_features["PLTR"]
   │
   ├── 4c. scoring.run("PLTR")
   │     ├── Linear weighted sum of 7 sub-scores (or XGBoost if enabled)
   │     ├── Apply alternative data modifier (P/C ratio, short %, insider)
   │     └── Return composite_score (0–100)
   │
   ├── 4d. risk_engine.run("PLTR")
   │     └── Return risk_score (0–10)
   │
   ├── 4e. signal_generator.run("PLTR", composite_score)
   │     ├── BUY if score >= 62, SELL if score <= 38, else HOLD
   │     ├── Compute confidence, price_target, stop_loss, time_horizon
   │     └── Return signal dict
   │
   ├── 4f. analyst.run("PLTR")   [async, may run concurrently with 4e]
   │     ├── Build context prompt from scores + indicators
   │     ├── POST to Anthropic Claude API
   │     ├── Parse JSON response → {thesis, bull_case, bear_case,
   │     │   catalysts, analyst_note}
   │     └── Return analyst_output (or rule-based fallback)
   │
   ├── 4g. Change detection
   │     ├── Compare new signal to previous stocks_signals["PLTR"].signal
   │     ├── If changed: notifier.send_alerts() for all users watching PLTR
   │     └── If changed: upsert new record → stocks_signal_history
   │
   └── 4h. Upsert stocks_signals["PLTR"] with all outputs

5. Return stocks_signals["PLTR"] as JSON response ──────────────────────────► HTTP 200
```

---

### 4.B Scheduled Pipeline: Every 30 Minutes During Market Hours

```
1. APScheduler fires market_pipeline job
   │
2. Market hours guard check
   ├── Weekend? → exit (no-op)
   └── Outside 9:30–16:00 ET? → exit (no-op)

3. Query all unique tickers across all watched_tickers documents:
   db.watched_tickers.distinct("ticker")

4. For each ticker in list (sequential, with inter-ticker delay):
   │
   └── pipeline.run(ticker)          [same steps 4a–4h as user-triggered flow]
         │
         └── On any exception for this ticker:
               log error, continue to next ticker (do not abort full run)

5. Log summary: "Pipeline complete: N tickers processed, M errors"
```

---

### 4.C Signal Settlement: `perf_tracker` Job (Daily at 6:00 UTC)

```
1. APScheduler fires perf_tracker job

2. Query stocks_signal_history for unsettled records:
   db.stocks_signal_history.find({
     "settled": false,
     "created_at": { "$lte": (now − 20 days) }
   })

3. For each unsettled history record:
   │
   ├── Fetch current price: yfinance.download(ticker, period="1d")
   │
   ├── Compute return:
   │     return_20d = (current_price − entry_price) / entry_price × 100
   │
   ├── Determine was_correct:
   │     BUY signal: was_correct = (return_20d > 0)
   │     SELL signal: was_correct = (return_20d < 0)
   │     HOLD signal: was_correct = (abs(return_20d) < 5.0)  [within ±5%]
   │
   └── Update record:
         db.stocks_signal_history.update_one(
           { "_id": record["_id"] },
           { "$set": {
               "settled": true,
               "current_price": current_price,
               "return_20d": return_20d,
               "was_correct": was_correct,
               "settled_at": now
           }}
         )

4. Log summary: "Settlement complete: N records settled"
```

## 6. Security Architecture

### 6.1 Authentication — JWT

- **Algorithm:** HS256 (HMAC-SHA256).
- **Signing secret:** Loaded exclusively from the `JWT_SECRET_KEY` environment variable. Never hardcoded.
- **Token expiry:** Configurable via `JWT_EXPIRE_HOURS` (default: 24 hours). The `exp` claim is embedded in the token payload.
- **Token transport:** Clients send the token in the `Authorization: Bearer <token>` HTTP header. Tokens are not stored in cookies (no CSRF risk).
- **Validation:** `dependencies.py:get_current_user` decodes and validates every request. Invalid or expired tokens raise `HTTPException(status_code=401)`.

### 6.2 Password Security — bcrypt

- Passwords are hashed using `passlib[bcrypt]` before storage.
- The bcrypt work factor is set to a minimum of 12 rounds.
- Password comparison uses `passlib`'s constant-time `verify` function to prevent timing attacks.
- Plaintext passwords are never logged, returned in responses, or stored anywhere.

### 6.3 CORS Policy

In production, `CORSMiddleware` is configured with an explicit list of allowed origins (e.g., `["https://sams-trading.pages.dev"]`). Wildcard origins (`*`) are disabled. The `allow_credentials=True` flag is set to permit the `Authorization` header in preflight requests.

### 6.4 Network Isolation — Cloudflare Tunnel

The backend API container binds to `0.0.0.0:8000` but the VPS firewall blocks inbound TCP connections on port 8000 from all external IPs. External HTTPS traffic is received at Cloudflare's edge, routed through the Cloudflare Tunnel (an outbound mTLS connection initiated by `cloudflared`), and forwarded to `http://api:8000` on the internal Docker bridge network. No public port exposure is required.

### 6.5 Container Security

- The FastAPI application container runs as a non-root user (`appuser`) defined in the Dockerfile.
- MongoDB is not bound to a public interface; it is accessible only on the internal Docker bridge network.
- No sensitive environment variables are baked into Docker images. All secrets are passed at runtime via Docker Compose environment files (`.env`, excluded from version control via `.gitignore`).

### 6.6 API Key Management

- All external API keys (`ANTHROPIC_API_KEY`, `FRED_API_KEY`, `FINNHUB_API_KEY`) are loaded from environment variables.
- Keys are never included in API responses returned to the frontend.
- Per-user alert settings that contain sensitive data (WhatsApp API key, Slack webhook URL) are stored in MongoDB but are excluded from the `GET /auth/me` response payload returned to the client.

```
│                                                                 │

```

### 7.2 VPS — Docker Compose

The production environment on the Hetzner VPS uses Docker Compose (`docker-compose.prod.yml`) with the following services:

| Service | Image | Ports | Restart |
|---|---|---|---|
| `api` | Built from `backend/Dockerfile` | `8000` (internal only) | `unless-stopped` |
| `mongo` | `mongo:7` | `27017` (internal only) | `unless-stopped` |
| `cloudflared` | `cloudflare/cloudflared` | None (outbound tunnel only) | `unless-stopped` |

All three containers share an internal Docker bridge network. No containers expose ports to the VPS host's public interface except for operator SSH access (port 22, protected by key-based auth).

MongoDB data is persisted to a named Docker volume (`mongo_data`) that survives container restarts and image rebuilds.

### 7.3 Backend CI/CD — GitHub Actions

The GitHub Actions workflow (`.github/workflows/deploy.yml`) triggers on push to `main` when files under `backend/**` change.

Deployment steps:
```
1. SSH into Hetzner VPS using a deploy key stored in GitHub Secrets
2. cd /opt/samstradingagent
3. git pull origin main
4. docker compose -f docker-compose.prod.yml up --build -d api
5. docker system prune -f  (clean up unused layers)
```

The `mongo` and `cloudflared` containers are not restarted during a backend deploy unless their configuration has changed. This minimizes downtime.

### 7.4 Frontend — Cloudflare Pages

The React frontend (`frontend/`) is connected to Cloudflare Pages via the GitHub integration. Any push to `main` that touches `frontend/**` triggers an automatic Pages build using the Vite build command (`npm run build`). The `dist/` directory is deployed to Cloudflare's global CDN.

Environment variables required for the frontend build:
- `VITE_API_BASE_URL` — set in the Cloudflare Pages dashboard, points to the Cloudflare Tunnel hostname (e.g., `https://api.sams-trading.com`).

### 7.5 Configuration Management

| Configuration Type | Storage Location |
|---|---|
| Backend secrets (API keys, JWT secret, DB URI) | `.env` file on VPS at `/opt/samstradingagent/.env`, excluded from git |

## 8. Scalability Considerations

### 8.1 Current Architecture Limits

The current single-VPS, single-worker deployment is well-suited for personal use with 1–10 users and up to ~100 watched tickers. Known bottlenecks at this scale:

| Bottleneck | Current Mitigation |
|---|---|
| Yahoo Finance rate limiting | Sequential ticker processing with configurable inter-ticker delay |
| Anthropic API latency (~2–5s per call) | Async call; cached in signal document; does not block signal response |
| Single Uvicorn worker | Sufficient for low concurrency; async I/O handles multiple simultaneous users |
| MongoDB single node | No replica set; acceptable for personal use with Docker volume backup |

### 8.2 Horizontal Scaling Path

If the system needs to serve a larger user base:

**Backend scaling:**
- Switch `uvicorn` to `gunicorn --workers N` with `UvicornWorker` to utilize multiple CPU cores.
- Move APScheduler jobs to a dedicated worker process (or replace with Celery + Redis/RabbitMQ) to avoid job duplication across workers.
- Introduce a Redis cache layer for signal documents to replace MongoDB as the hot cache, reducing read load on the database.

**Database scaling:**
- Add a MongoDB replica set (1 primary + 2 secondaries) for read scaling and automatic failover.
- Add an index on `stocks_signals.updated_at` for cache expiry queries under high ticker volumes.

**External API scaling:**
- Yahoo Finance: at high ticker volumes, parallelize ingestion across multiple worker processes with back-off and retry logic.
- Anthropic: batch report generation during off-peak hours; implement a queue to avoid concurrent rate-limit exhaustion.

### 8.3 Current Rate Limit Posture

| External API | Free Tier Limit | Current Usage Pattern |
|---|---|---|
| Yahoo Finance | Unspecified; rate-sensitive | Sequential, 1 ticker at a time, with delay |
| Finnhub | 60 calls/minute | One call per ticker per pipeline run |
| FRED | 120 calls/minute | Cached 24h; typically 4 series per run |
| Anthropic | RPM/TPM per tier | One call per ticker per pipeline run; ~1,024 tokens out |
| CallMeBot | ~5 messages/minute | Event-driven only; low frequency |

### 8.4 Observability Roadmap

Current observability is provided by `structlog` JSON logs written to stdout, captured by Docker. For future scaling:
- Add Prometheus metrics endpoint (`/metrics`) via `prometheus-fastapi-instrumentator`.
- Ship logs to a hosted log aggregation service (e.g., Grafana Cloud Loki or Cloudflare Logpush).
- Add distributed tracing via OpenTelemetry for end-to-end pipeline latency attribution.
