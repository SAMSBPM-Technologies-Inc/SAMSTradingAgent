## 1. Product Overview

**SAMSTradingAgent** is a stock analysis and decision-support platform that aggregates technical indicators, fundamental data, macroeconomic conditions, AI-generated research notes, and alternative data (options flow, short interest, insider trading) to produce actionable **BUY / SELL / HOLD** signals with confidence scores for individual equity tickers.

The platform is designed for personal research and portfolio decision support. It is **not** a broker, dealer, or registered investment adviser. All signals and analysis are informational only and carry explicit disclaimers. Users retain full responsibility for their investment decisions.

### 1.1 Core Value Proposition

| Capability | Description |
|---|---|
| Signal generation | BUY/SELL/HOLD signal per ticker with a composite score (0–100) and confidence percentage |
| AI analyst reports | Multi-paragraph investment thesis generated by Claude (Anthropic), including bull/bear cases and key risks |
| Technical analysis | RSI, MACD, Bollinger Bands, 20/50-day moving averages displayed per ticker |
| Alternative data | Options put/call ratio, short interest %, insider buy/sell count |
| Performance tracking | 20-day signal settlement, win rate statistics, average return by signal type |
| Real-time alerts | Slack and WhatsApp notifications on signal flips and high-conviction events |
| Automated pipeline | Background refresh every 30 minutes during US market hours; pre-market sweep at 8:00 AM ET |

### 1.2 Disclaimer

> **Investment Risk Notice:** SAMSTradingAgent is a research and decision-support tool. Signals produced by this system do not constitute financial advice, a recommendation to buy or sell any security, or a guarantee of future performance. All investing involves risk, including possible loss of principal. Users should conduct their own due diligence before making any investment decisions.

## 3. Functional Requirements

Requirements are grouped by feature area and numbered **FR-001** through **FR-035**.

---

### 3.1 Authentication and User Management

#### FR-001 — User Registration
The system shall allow a new user to register by providing an email address, a password, and an optional display name. The email must be unique across all users. The system shall reject duplicate email addresses with a clear error message.

#### FR-002 — Password Security
The system shall hash all passwords using bcrypt before storing them. Plaintext passwords must never be persisted to the database or written to any log output.

#### FR-003 — User Login
The system shall allow a registered user to authenticate using their email and password. On successful authentication the system shall issue a signed JWT access token.

#### FR-004 — JWT Token Issuance
The JWT token shall be signed using the HS256 algorithm with a server-side secret. Tokens shall have a configurable expiry (default: 24 hours). Tokens shall carry the user's unique identifier as the `sub` claim.

#### FR-005 — Authenticated Endpoints
All watchlist, analysis, signal, report, performance, and alert endpoints shall require a valid JWT token. Requests without a token or with an expired/invalid token shall receive an HTTP 401 response.

#### FR-006 — Display Name
The system shall allow authenticated users to set or update a display name that is separate from their email address. The display name shall be displayed in the UI header and profile page.

#### FR-007 — Profile Management
The system shall provide a profile page where users can update their display name, configure alert destinations (Slack webhook URL, WhatsApp phone number and API key), and send test notifications to verify their alert setup.

---

### 3.2 Watchlist Management

#### FR-008 — Add Ticker to Watchlist
An authenticated user shall be able to add a valid equity ticker symbol to their personal watchlist. The ticker shall be normalized to uppercase. Adding an already-watched ticker shall be idempotent (no error, no duplicate).

#### FR-009 — Remove Ticker from Watchlist
An authenticated user shall be able to remove a ticker from their watchlist. Removing a ticker that is not on the watchlist shall return a graceful response (no error).

#### FR-010 — View Watchlist
The system shall return the authenticated user's watchlist with each ticker's current signal, composite score, confidence, and price. Tickers shall be sorted by composite score (descending) so highest-conviction ideas appear first.

#### FR-011 — Per-User Isolation
Each user's watchlist shall be stored independently. A ticker on User A's watchlist shall have no effect on User B's watchlist. Signal cache data, however, is shared across users to reduce redundant API calls.

---

### 3.3 Ticker Analysis

#### FR-012 — Analysis Endpoint
The system shall expose an endpoint to analyze a single ticker (e.g., `GET /analyze?ticker=AAPL`). This endpoint shall trigger the full analysis pipeline if no cached result exists (or if the cache has expired) and return the signal output.

#### FR-013 — Signal Output
The analysis response for each ticker shall include:
- **Signal:** one of `BUY`, `SELL`, or `HOLD`
- **Composite Score:** integer 0–100 representing overall conviction
- **Confidence:** percentage (0–100%) derived from signal-to-threshold margin
- **Price Target:** estimated upside/downside price level
- **Stop Loss:** suggested risk management level
- **Time Horizon:** short (days), medium (weeks), or long (months)
- **Current Price:** last known closing price
- **Timestamp:** when the signal was generated

#### FR-014 — Signal Cache
Signal results shall be cached in MongoDB with a 30-minute TTL. Subsequent requests for the same ticker within the TTL shall return the cached result without re-running the pipeline. An authenticated user shall be able to force a cache bypass to trigger a fresh analysis.

#### FR-015 — Force Refresh
The system shall support an optional `force_refresh=true` query parameter on the analysis endpoint. When this flag is set, the system shall bypass the cache and run the full ingestion and scoring pipeline regardless of cache age.

---

### 3.4 Technical Indicators Display

#### FR-016 — Technical Indicators
The analysis response shall include the following computed technical indicators for display in the UI:

| Indicator | Description |
|---|---|
| RSI-14 | 14-period Relative Strength Index |
| MACD | MACD line, signal line, and histogram |
| Bollinger Bands | Upper band, lower band, and band width |
| MA-20 | 20-day simple moving average |
| MA-50 | 50-day simple moving average |
| ATR | Average True Range (volatility proxy) |
| Volume Ratio | Current volume vs. 20-day average volume |

---

### 3.5 Sub-Scores

#### FR-017 — Sub-Score Breakdown
The analysis response shall include a breakdown of the 7 sub-scores that contribute to the composite score, so users understand what is driving the signal:

| Sub-Score | Weight (approximate) |
|---|---|
| Trend Score | Based on MA alignment and price position |
| Momentum Score | Based on RSI and MACD |
| Volatility Score | Based on Bollinger Band width and ATR |
| Volume Score | Based on volume vs. average |
| Fundamental Score | Based on P/E, revenue growth, FCF, D/E |
| Sentiment Score | Based on Finnhub news VADER sentiment |
| Macro Score | Based on FRED rates, CPI, VIX, yield curve |

---

### 3.6 Alternative Data

#### FR-018 — Options Flow
The system shall retrieve and display the options put/call ratio for each ticker. A ratio below 0.7 is considered bullish; above 1.2 is considered bearish. This ratio shall influence the composite score via an alternative data modifier.

#### FR-019 — Short Interest
The system shall retrieve the current short interest percentage of float for each ticker via yfinance. High short interest (above 15%) in a rising stock is treated as a potential short squeeze catalyst.

#### FR-020 — Insider Transactions
The system shall retrieve the count of insider buy and sell transactions over the trailing 90 days for each ticker. Net insider buying is treated as a positive signal modifier.

---

### 3.7 AI Analyst Report

#### FR-021 — AI-Generated Thesis
The system shall generate a structured analyst report for each ticker using Anthropic Claude. The report shall include:
- **Investment Thesis:** 2–3 paragraph narrative summary of the opportunity or risk
- **Bull Case:** 3–5 bulleted reasons the stock could outperform
- **Bear Case:** 3–5 bulleted risks or headwinds
- **Key Catalysts:** near-term events or data points that could move the stock
- **Analyst Note:** closing commentary on signal conviction

#### FR-022 — Report Caching
AI-generated reports shall be cached alongside the signal output. Reports shall not be regenerated on every request. The cache TTL for reports shall match the signal cache TTL (30 minutes) unless a force refresh is triggered.

#### FR-023 — Fallback Behavior
If the Anthropic API is unavailable, returns an error, or no API key is configured, the system shall fall back to a rule-based report template that populates the same fields using the computed sub-scores and indicator values. The UI shall indicate when a report is AI-generated vs. rule-based.

#### FR-024 — Separate Report Endpoint
The system shall expose a dedicated endpoint (e.g., `GET /report/{ticker}`) to retrieve the analyst report independently from the signal endpoint, allowing the UI to lazy-load the report after initial signal rendering.

---

### 3.8 Performance Tracking

#### FR-025 — Signal History Recording
Each time a signal is generated or updated, the system shall write a record to the signal history collection capturing: ticker, signal type, score, composite score, timestamp, and the price at signal time.

#### FR-026 — 20-Day Outcome Settlement
The system shall run a daily settlement job (at 6:00 UTC) that identifies signal history records that are 20 calendar days old and have not yet been settled. For each such record, the job shall fetch the current price and compute the return relative to the signal-time price. The record shall be updated with `was_correct` (boolean) and `return_20d` (float).

#### FR-027 — Performance Statistics
The system shall expose an endpoint (e.g., `GET /performance`) that returns aggregate performance statistics for the authenticated user's watchlist, including:
- Total signals settled
- Win rate by signal type (BUY, SELL, HOLD)
- Average return across all settled signals
- Average return by signal type

---

### 3.9 Notifications and Alerts

#### FR-028 — Signal Flip Alert
The system shall send a real-time notification to the user's configured Slack webhook and/or WhatsApp destination when a ticker's signal changes (e.g., from HOLD to BUY, or from BUY to SELL). Notifications shall include the ticker, old signal, new signal, composite score, and current price.

#### FR-029 — High-Conviction Alert
The system shall send a notification when a ticker's composite score exceeds a configurable high-conviction threshold (default: 75 for BUY, below 30 for SELL) and the previous score was below the threshold.

#### FR-030 — Daily Digest
The system shall send a morning digest notification at 9:00 AM ET on weekdays to any user who has alerts configured. The digest shall summarize the current signal status of all tickers on the user's watchlist: signal, composite score, and any tickers that have changed signal since the previous day.

#### FR-031 — Test Notification
From the profile page, an authenticated user shall be able to trigger a test notification to verify that their Slack webhook or WhatsApp integration is correctly configured. The test message shall be clearly labeled as a test.

#### FR-032 — Alert Settings Persistence
Users' alert configurations (Slack webhook URL, WhatsApp phone number, WhatsApp API key, enable/disable flags per channel) shall be stored in the user document in MongoDB and persist across sessions.

---

### 3.10 Background Pipeline

#### FR-033 — Scheduled Market-Hours Refresh
The system shall run an automated analysis pipeline on a configurable interval (default: every 30 minutes) during US market hours (9:30 AM – 4:00 PM ET, Monday through Friday). The pipeline shall process all tickers that are on at least one user's watchlist.

#### FR-034 — Pre-Market Sweep
The system shall run a full watchlist refresh at 8:00 AM ET on weekdays, before market open. This ensures signals are populated and fresh when users log in at market open.

#### FR-035 — Change Detection
The pipeline shall compare each newly computed signal against the previously stored signal. If the signal or composite score has changed materially (configurable threshold), the pipeline shall fire alert notifications and append a new entry to the signal history collection.

---

### 3.11 User Interface

#### FR-036 — Light/Dark Mode
The UI shall support a light mode and a dark mode. The user's preference shall be persisted in browser local storage and applied on every page load without requiring a login.

#### FR-037 — Buyer's and Seller's Guide
The system shall provide a contextual guide page offering a "Buyer's Guide" view and a "Seller's Guide" view. These views shall explain how to interpret the signals, sub-scores, and indicators in the context of entering vs. exiting a position.

## 4. Non-Functional Requirements

---

### 4.1 Performance

#### NFR-001 — Cached Response Latency
API responses for tickers with a valid cache entry shall be returned within **2 seconds** under normal load conditions.

#### NFR-002 — Fresh Pipeline Latency
API responses that require a full pipeline run (cache miss or force refresh) shall complete within **30 seconds**. Ingestion is the bottleneck; all sub-calls are made asynchronously where possible.

#### NFR-003 — UI Time to Interactive
The frontend shall achieve interactive state within **3 seconds** on a standard broadband connection after initial page load. Lazy loading shall be used for the AI analyst report section.

---

### 4.2 Reliability

#### NFR-004 — Graceful Degradation — Finnhub
If the Finnhub API is unavailable or returns an error, the system shall proceed with analysis using zero or neutral sentiment scores and shall log a warning. The signal shall not be blocked.

#### NFR-005 — Graceful Degradation — FRED
If the FRED macroeconomic API is unavailable, the system shall use the last-known macro values cached in MongoDB. If no cached values exist, the macro sub-score shall default to neutral (50). The signal shall not be blocked.

#### NFR-006 — Graceful Degradation — Anthropic
If the Anthropic Claude API is unavailable, the system shall use the rule-based analyst report generator (see FR-023). The system shall never surface a raw API error to the end user.

#### NFR-007 — Graceful Degradation — Yahoo Finance
Yahoo Finance is the primary price data source. If Yahoo Finance returns an error or empty data for a ticker, the pipeline shall skip that ticker, log an error, and move to the next ticker in the queue. Downstream collections shall not be updated for the failed ticker.

#### NFR-008 — Docker Restart Policy
All Docker containers (API, MongoDB, cloudflared) shall be configured with `restart: unless-stopped` to automatically recover from process crashes or VPS reboots without operator intervention.

---

### 4.3 Security

#### NFR-009 — Password Storage
Passwords shall be stored exclusively as bcrypt hashes. The bcrypt work factor shall be at minimum 12 rounds.

#### NFR-010 — JWT Security
JWT tokens shall use the HS256 algorithm. The signing secret shall be loaded from an environment variable and never hardcoded. Tokens shall expire after a configurable period (default 24 hours). Expired tokens shall be rejected with HTTP 401.

#### NFR-011 — CORS Policy
The FastAPI backend shall enforce an explicit CORS allow-list. In production, only the deployed Cloudflare Pages domain(s) shall be permitted as request origins. Wildcard CORS (`*`) shall not be used in production.

#### NFR-012 — No Credentials in Responses
API responses shall never include hashed passwords, JWT signing secrets, external API keys, or any other sensitive credential. User response objects shall include only the user ID, email, and display name.

#### NFR-013 — No Public Port Exposure
The backend API port (8000) shall not be exposed to the public internet. All external traffic shall be routed exclusively through the Cloudflare Tunnel (`cloudflared`). The VPS firewall shall block inbound traffic on port 8000 from public IPs.

#### NFR-014 — Non-Root Container User
The FastAPI application Docker container shall run as a non-root user to limit the blast radius of any container escape vulnerability.

---

### 4.4 Scalability

#### NFR-015 — Per-User Data Isolation
The data model shall support an arbitrary number of users each with independent watchlists. Signal cache data (stocks_raw, stocks_features, stocks_signals) is shared across users to avoid redundant computation.

#### NFR-016 — Concurrent Access
The FastAPI application shall handle concurrent user requests using async I/O. All database and HTTP calls within the service layer shall be awaited. Blocking operations shall not be performed on the async event loop.

#### NFR-017 — API Rate Limit Compliance
The background pipeline shall space out individual ticker ingestion calls to Yahoo Finance with configurable inter-ticker delays to respect rate limits and avoid IP-level throttling.

---

### 4.5 Availability

#### NFR-018 — Cloudflare Tunnel Availability
The Cloudflare Tunnel shall provide the ingress path for all external traffic. The tunnel shall be started as a Docker container and shall restart automatically on failure. Cloudflare's global network provides high availability for the edge layer.

#### NFR-019 — Deployment Zero-Downtime Target
The GitHub Actions deployment workflow shall use Docker Compose `up --build -d` which replaces containers with minimal downtime. Full zero-downtime blue/green deployment is a future enhancement.

---

### 4.6 Data Freshness

#### NFR-020 — Signal Cache TTL
Cached signals shall expire after **30 minutes**. After expiry, the next request for that ticker shall trigger a full pipeline run to refresh the data.

#### NFR-021 — Pre-Market Signal Readiness
The pre-market sweep at 8:00 AM ET shall ensure that all watched tickers have a fresh signal computed before the 9:30 AM ET market open, so users are not waiting for pipeline runs during the first minutes of trading.

---

### 4.7 Observability

#### NFR-022 — Structured Logging
The backend shall emit structured JSON logs using `structlog`. Each log event shall include at minimum: timestamp, log level, module name, and a message. Pipeline runs shall log per-ticker start/complete/error events.

#### NFR-023 — Error Reporting
Unhandled exceptions in API route handlers shall be caught by a global exception handler in `main.py`, logged at ERROR level with a full traceback, and returned to the client as a standardized JSON error response (HTTP 500) that does not expose internal stack traces.

## 5. Data Requirements

### 5.1 Price History

- **Source:** Yahoo Finance (via `yfinance` Python library)
- **Granularity:** Daily OHLCV (Open, High, Low, Close, Volume) bars
- **Lookback:** 90 calendar days per ticker
- **Frequency:** Fetched fresh on every pipeline run; stored in `stocks_raw.bars`

### 5.2 External API Dependencies

| API | Provider | Tier | Purpose |
|---|---|---|---|
| Yahoo Finance | Yahoo / `yfinance` | Free (unofficial) | OHLCV price history, fundamentals, options data, insider transactions |
| Finnhub | Finnhub.io | Free tier | News headlines for VADER sentiment scoring |
| FRED | Federal Reserve Bank of St. Louis | Free (API key required) | Macroeconomic indicators: Fed Funds Rate, CPI, VIX, yield spread |
| Anthropic Claude | Anthropic | Paid (API key required) | AI analyst report generation |
| CallMeBot | CallMeBot.com | Free | WhatsApp notification delivery |
| Slack | Slack | Free (incoming webhook) | Slack notification delivery |

### 5.3 MongoDB Collections

The system uses six MongoDB collections:

| Collection | Primary Key | Purpose |
|---|---|---|
| `stocks_raw` | `ticker` (unique) | Raw ingested data: OHLCV bars, Finnhub sentiment, yfinance fundamentals, FRED macro, alternative data |
| `stocks_features` | `ticker` (unique) | Computed technical indicators and 7 sub-scores |
| `stocks_signals` | `ticker` (unique) | Current signal: BUY/SELL/HOLD, composite score, confidence, analyst output, alternative data |
| `stocks_signal_history` | `(ticker, hour_bucket)` (unique) | Historical signal records for performance settlement |
| `watched_tickers` | `(user_id, ticker)` (unique) | Per-user watchlist entries |
| `users` | `email` (unique) | User accounts: hashed password, display name, alert settings |

### 5.4 Data Volume Estimates

| Collection | Expected Records (per 50 tickers, 10 users) |
|---|---|
| `stocks_raw` | ~50 documents (one per ticker) |
| `stocks_features` | ~50 documents |
| `stocks_signals` | ~50 documents |

## 6. Constraints and Assumptions

### 6.1 Yahoo Finance Terms of Service
Yahoo Finance data is accessed via the `yfinance` open-source library. This data source is suitable for **personal and research use**. Commercial redistribution of Yahoo Finance data or use in a commercial product without licensing is not permitted. This constraint limits production deployment to personal/research contexts.

### 6.2 Anthropic API Key Required for AI Reports
The AI analyst report feature (FR-021) requires a valid Anthropic API key and incurs per-token cost. If no key is configured (`ANTHROPIC_API_KEY` environment variable is absent), the system falls back to the rule-based report template. The rule-based fallback produces structurally identical output but with lower prose quality.

### 6.3 WhatsApp / CallMeBot Pre-Authorization
WhatsApp notifications via CallMeBot require the recipient to manually send a one-time authorization message to the CallMeBot WhatsApp number before the first notification can be delivered. Users must complete this step before configuring WhatsApp alerts in their profile.

### 6.4 Backtesting Not Production-Ready
The `backtesting.py` service is a stub implementation controlled by the `ENABLE_BACKTESTING` environment flag (default: `false`). The backtesting feature is not exposed in the production UI and is excluded from all SLA and reliability guarantees. It exists as a scaffold for future development.

### 6.5 Market Hours Dependency
Signal freshness is designed around US equity market hours (9:30 AM – 4:00 PM ET, Monday–Friday). The background pipeline pauses outside of these hours. Tickers traded on non-US exchanges or with extended-hours activity will have signals that do not reflect after-hours price moves.

### 6.6 Single-VPS Deployment
The current deployment model targets a single Hetzner VPS running Docker Compose. This is sufficient for personal/small-group use but is not architected for high-availability multi-region deployment without additional infrastructure work.

### 6.7 FRED API Key Required
Macroeconomic data from FRED requires a free API key from the Federal Reserve Bank of St. Louis. If the `FRED_API_KEY` environment variable is not set, the macro sub-score will default to neutral (50) and a warning will be logged.

## 7. Out of Scope

The following capabilities are explicitly out of scope for SAMSTradingAgent v1.x:

| Out of Scope Item | Notes |
|---|---|
| Direct trade execution | SAMSTradingAgent does not connect to any brokerage API. It produces signals only. |
| Portfolio tracking with actual P&L | The system does not know how many shares a user holds. Performance tracking is signal-based, not position-based. |
| Options trading analysis | The system reads options put/call ratios as an alternative data input but does not analyze or recommend options strategies. |
| Real-time streaming prices (tick data) | All price data uses daily OHLCV bars. Intraday tick or minute-bar streaming is not supported. |
| Mobile native app | The frontend is a web application (React/Vite/TypeScript). It is PWA-capable (installable on mobile) but is not a native iOS or Android application. |
| Multi-asset classes | The system is designed for US equities only. Cryptocurrency, fixed income, commodities, and forex are not supported. |
| Social/collaborative features | There is no sharing of watchlists, signals, or analyst reports between users. All data is private per user. |
| Regulatory compliance (FINRA, SEC) | SAMSTradingAgent is a personal research tool and is not registered as an investment adviser, broker-dealer, or research firm. |
| Automated trade journaling | The system does not record actual trades, fill prices, or position sizes. |
